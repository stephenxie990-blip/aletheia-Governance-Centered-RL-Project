## 3. 这轮审计修正了什么错误判断

## 4. 当前真正的根因收敛

### 4.1 `v96` 的改善为什么没法从 `1250` 传到 `1500`

`v96` 的 `midwater` 修复确实有效，但只在 `post_entry_soft` 阶段有效：

- `1100/1200`: `stage = post_entry_soft`
- `actor/post_entry_soft_midwater_guard_active = 1`
- `actor/negative_adv_guard_scale = 0.75`
- `imag/continue_prob_cap_dynamic = 0.93`
- `imag/effective_horizon ≈ 8.23`

但一旦进入 `1300`：

- `stage = persistence`
- `imag/controller_post_entry_persistence_escape_active = 1`
- `actor/post_entry_soft_midwater_guard_active = 0`
- `actor/negative_adv_guard_scale = 1.0`
- `imag/continue_prob_cap_dynamic = 0.86`
- `imag/effective_horizon ≈ 5.78`

也就是说，`1250` 的抬升并不是自然衰减掉了，而是发生了一个明确的控制器离散切换：

1. `post_entry_soft` 的 band-aware guard 生效。
2. 进入 `persistence_escape` 后，band-aware guard 被清空。
3. 同时 `cap` 从 `0.93` 切到 `0.86`，`actor_scale` 也从 soft/post-entry 系列落回 persistence 系列。
4. 于是 `midwater` 给 `1250` 带来的增益，没有被后续阶段继承。

### 4.2 这不是简单“参数不够强”，而是“跨模块连续性丢失”

代码审计点：

- `post_entry_soft` 的 `midwater/highwater` 逻辑只在 `controller_stage == post_entry_soft` 分支里增强。
- 当 `persistence_escape_soft_guard_active` 为真时，代码只回退到：
  - `adaptive_imag_persistence_escape_negative_adv_actor_scale`
  - `adaptive_imag_persistence_escape_negative_adv_critic_boost`
- 但不会继续带上：
  - `midwater ramp`
  - `midwater/highwater critic boost`
  - `soft cap floor`
  - `soft actor scale floor`

结果就是：

- 我们已经修过“是否继承 soft guard”这个一阶问题。
- 但还没修“是否继承 soft guard 的 band-specific 强度与软着陆几何”这个二阶问题。

### 4.3 `v87` 为什么能 solved，而 `v88/v96` 不能

新审计结论不是“`v87` 走了更高级阶段”，而是：

- `v87` 也停在 `persistence`
- 但它在 `persistence` 阶段仍保住了更健康的 imagined dynamics

对比 `1500` 训练步前的指标：

- `v87`:
  - `target_mean = 7.75`
  - `continue_prob_mean = 0.804`
  - `continue_prob_mean_raw = 0.912`
  - `effective_horizon = 6.01`
- `v88`:
  - `target_mean = 6.16`
  - `continue_prob_mean = 0.687`
  - `continue_prob_mean_raw = 0.782`
  - `effective_horizon = 5.78`
- `v96`:
  - `target_mean = 5.33`
  - `continue_prob_mean = 0.616`
  - `continue_prob_mean_raw = 0.702`
  - `effective_horizon = 5.58`

含义：

- `seed5` 并不是输在“negative advantage 更负”。
- 真正更稳定区分 solved/failed 的，是进入 `persistence` 后 imagined continue / horizon / target 是否还能维持住。
- 因此当前更核心的问题是：`seed5` 在 `post_entry_soft -> persistence_escape` 交界处，控制器切得太陡，导致 imagined dynamics 失速。

## 5. 当前修复成果的审计结论

### 5.1 已经证明有效的成果

1. `TrainingStep.global_step` 同步 bug 修复是正确且必要的。
2. `midwater` 不是错误方向，它已经真实把 `seed5` 的 `1250` 从 `83` 抬到 `95/99`。
3. 现有 `persistence_escape` guard 继承修复解决了一阶“保护完全丢失”的 bug。
4. 项目具备两条 solved 形态：
   - `highwater commit -> post_solved`
   - `persistence` 直接冲到 `500`

### 5.2 已证伪或应降级的判断

1. “继续扫 `midwater boost / ramp` 就能解决 `1500`”应降级。
2. “主矛盾已经完全收敛到 `commit/release/post_solved handoff`”应修正。
3. “只要增强 `persistence_escape critic boost` 就能解决”已被 `v95` 证伪。

### 5.3 当前测试缺口

现有测试已覆盖：

- `persistence_escape` 是否继承 `post_entry_soft` 基础 guard 强度。
- `post_entry_soft` 的 `midwater/highwater` 自身逻辑。

但未覆盖：

- `post_entry_soft midwater/highwater` 进入 `persistence_escape` 后，是否连续继承 band-specific boost / ramp。
- `post_entry_soft -> persistence` 切换时，`cap / actor_scale / guard strength` 是否出现不合理台阶跳变。

这就是当前修复分支还能“局部看对、整体仍塌”的核心测试缺口。

## 6. 深思后的发展方向

### 方向 A：优先级最高

做 `post_entry_soft -> persistence_escape` 的连续性修复，而不是继续扫单点参数。

具体应优先设计为：

1. `persistence_escape` band-aware guard inheritance
2. `persistence_escape` soft-cap / soft-actor floor continuity
3. 只在 unresolved external post-entry 仍成立时保持这份 continuity
4. 一旦 commit 成功、release 成立或 post_solved 成立，再退出 continuity

这条方向的目标不是“更强地刹车”，而是“不要在 1250 之后突然换一套更硬的动力学”。

### 方向 B：同步补测试

先补两类集成测试：

1. `midwater/highwater` 在 `persistence_escape` 中的继承测试
2. `post_entry_soft -> persistence` 切换时 `cap/actor_scale/guard` 连续性测试

如果没有这两类测试，后续任何修复都仍然可能再次出现“1250 提升，1500 反而更差”的回归。

### 方向 C：实验策略

下一轮不建议继续大范围扫参数，而建议做最小变量结构实验：

1. 只修 `persistence_escape` 的 band-aware critic/guard continuity
2. 再单独修 `soft cap / actor floor` continuity
3. 最后视结果决定是否需要混合修复

实验评价顺序：

1. 先看 `1300` 是否不再从 `0.93/8.2` 直接跳到 `0.86/5.7`
2. 再看 `1250 -> 1500` 的 `continue_raw / effective_horizon / target_mean`
3. 最后才看 `1500 eval`

## 7. 最终判断

当前项目并没有走进“纯 imag 无法修复”的死路。

真正的问题是：

- 我们已经把 `seed5` 拉回了更高的 `1250` 带
- 但控制器在 `post_entry_soft -> persistence_escape` 的边界上，仍然存在架构级的离散跳变
- 这导致 `midwater` 的收益无法跨阶段传递

因此，下一轮最值得做的，不是再问“要不要更长步数”或“要不要再扫 boost”，而是直接修：

- `unresolved external post-entry` 在 `persistence_escape` 中的连续控制几何

这才是当前最接近 `seed5 1500=500` 的主战场。
