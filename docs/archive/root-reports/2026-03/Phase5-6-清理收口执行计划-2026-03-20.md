# Phase 5/6 清理收口执行计划

## 1. 目标

本计划不是继续“修模型”，而是把已经证明无力完成主修复职责的 controller 脚手架做止损式收口：

- 把 `controller` 从主合同降级为最小补偿层
- 删掉纯审计、纯报表、纯解释性信号的外围脚手架
- 收缩配置面、测试面、指标面
- 最终把系统工程边界收口到 `contract / arbiter / minimal compensation`

## 2. 不做什么

- 不在本计划内继续发散新的 Phase 4 实验刀口
- 不把 `WM core` 当作本轮 cleanup 的主假设
- 不做“一把全删”的高风险重构
- 不为了保留历史脚手架而继续扩大指标和配置表面

## 3. 清理原则

### 3.1 总原则

先删不影响训练行为的外围，再折叠仍在 live path 上的控制逻辑。

### 3.2 风险原则

凡是仍然直接影响以下行为的代码，一律不允许第一批直接删除：

- `continue cap`
- `base_return_cap`
- `actor scale`
- `post-trigger hysteresis`
- `controller_stage` 主指标写回

### 3.3 收口原则

每一批只解决一个主问题：

1. 减外围
2. 减解释层
3. 折主控制器
4. 清配置和测试
5. 做最终对账

## 5. 实施批次

### Batch 0：冻结基线与清理清单

目标：

- 固定 cleanup 前基线
- 把“删什么、留什么、为什么”固化成 manifest

动作：

- 固定一份 pre-cleanup 基线验证口径
- 列出将被删除的模块、API 出口、配置簇、测试文件
- 固定最小回归集

验证：

- `compileall`
- 最小训练集成测试基线通过
- 清理前指标名清单落盘

完成标准：

- 有明确 manifest
- 有最小回归命令集
- 有回滚锚点

### Batch 1：删除 audit-only 模块

目标：

- 先砍掉不承载训练行为的外围报表/审计链

范围：

- `post_entry_*audit*`
- `controller/*audit*`
- `aletheia_api.py` 中对应导入、产物生成与 summary 输出
- 对应 audit/template/precursor 测试

动作：

- 删除 audit 模块文件
- 删除 API 中 `post_entry_audit` 的导入和输出路径
- 删除只验证 audit/report 产物的测试

风险：

- 训练行为风险低
- 但会打断现有离线审计产物输出

验证：

- `python3 -m compileall aletheia`
- `./.venv/bin/python -m unittest` 跑非 audit 主链回归
- 确认训练入口不再引用已删模块

完成标准：

- 训练代码和 API 中不再 import audit-only 模块
- 所有 audit-only 测试删除或替换

### Batch 2：删除 signal/schema/invariants 解释层

目标：

- 收掉 controller 的解释性信号系统和关系 schema

范围：

- `controller/signals.py`
- `controller/schema.py`
- `controller/invariants.py`
- `controller/__init__.py`
- 训练里 `build_controller_signal_snapshot` 调用及对应指标输出
- 对应 controller signal/relation 测试

动作：

- 删掉训练内 signal snapshot 生成和相关指标写回
- 删掉 controller 包中只服务解释/审计的公开接口
- 删掉 controller signal/relation 单测

风险：

- 不直接改变主控制逻辑
- 但会减少最终对账的中间可解释量

验证：

- 主训练循环仍能完成 imagined batch 和 metrics 写回
- 不再残留 `imag/signal_*` 指标出口

完成标准：

- controller 解释层不再挂在训练主循环上
- controller 包只剩 live compensation 所需最小内容

### Batch 3：把 live controller 折叠成最小补偿层

目标：

- 把 stage-heavy controller 从“主合同”降成“补偿层”

范围：

- `aletheia_train.py` 中所有 `controller_stage` 分支
- `pretrigger / entry_probe / post_entry / pending / handoff / persistence / post_solved`
- `latch / bypass / rescue / handoff` 状态变量
- 对应 config 和 integration tests

策略：

- 不是整包删除
- 先压缩成一个最小补偿接口，例如：
  - 是否进入补偿
  - actor scale floor/cap
  - return-cap compensation
  - persistence tail compensation

动作：

- 先合并阶段分支，去掉形态学区分过强的 stage machine
- 把 stage 字符串和大量中间状态压成少量 compensation 状态
- 删除冗余 `latch / bypass / rescue` 分支

风险：

- 这是全计划最高风险的一批
- 改的是 live behavior，不是外围报表

验证：

- 关键训练集成测试补齐到“最小补偿层”新口径
- 对比 cleanup 前后的核心行为指标：
  - `imag/continue_prob_cap`
  - `actor/post_trigger_scale`
  - `actor/base_return_cap_*`
  - `actor/weights_*`
  - `imag/effective_horizon`

完成标准：

- 训练行为仍可运行
- controller 只剩补偿接口，不再保留复杂 stage machine

### Batch 4：清理 config / test / metrics 面

目标：

- 把历史脚手架留下的参数、测试、重复指标彻底收口

范围：

- `aletheia_config.py` 中失效 controller 配置
- `test_training_loop_integration.py` 中 stage-heavy 断言
- 重复或只服务脚手架的指标

动作：

- 删除废弃 config 字段
- 将 integration tests 改写为围绕最小补偿层断言
- 删除重复指标，保留最终对账所需最小指标集

验证：

- 配置类可正常构造
- 无悬空字段访问
- 核心测试口径变短、变稳

完成标准：

- 配置面显著缩小
- 测试不再围绕旧 stage 名称展开
- 重复指标出口清零

### Batch 5：终局验证与对账

目标：

- 完成 Phase 6 的最终验收

动作：

- 跑完整 compile + unit/integration 回归
- 生成清理前后对账图
- 形成最终保留边界：
  - `contract`
  - `arbiter`
  - `minimal compensation`

最终验收问题：

1. controller 是否已经不是主合同
2. 是否清掉了冗余 `latch / bypass / rescue`
3. contract / arbiter 边界是否清楚
4. 配置、测试、指标是否已明显收缩

## 6. 建议实施顺序

唯一推荐顺序：

1. `Batch 0`
2. `Batch 1`
3. `Batch 2`
4. `Batch 3`
5. `Batch 4`
6. `Batch 5`

不建议的顺序：

- 直接先做 `Batch 3`
- 直接全删 `controller_stage`
- 先清 config 再清 live path

## 8. 本计划的完成定义

当以下条件同时成立时，Phase 5/6 可视为完成：

- `controller` 不再作为主合同存在
- 训练主链只保留最小补偿层
- audit-only / signal-only 脚手架已删除
- config/test/metrics 表面显著缩小
- `contract / arbiter / compensation` 边界可用一句话说清
- 清理前后验证与对账文档完整
