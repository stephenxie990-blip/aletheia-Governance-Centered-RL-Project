## 1. 目的

## 2. 分层定义

本矩阵统一使用 5 个故障层:

### `WM core`

指 teacher-forced 世界模型预测核心本体:

- RSSM
- reward head
- continue head
- recon / KL / predictive loss

对应代码主链:

- `[aletheia_train.py](/Users/zhangsan/Desktop/缸中之脑v5.6/aletheia/aletheia_train.py)` 中 world model 更新路径 `observe_sequence -> build_trajectory -> compute_loss`
- `[aletheia_world_model.py](/Users/zhangsan/Desktop/缸中之脑v5.6/aletheia/aletheia_world_model.py)` 中 `PredictiveEngine.compute_loss()`

### `imagined geometry`

指 actor/critic 真正训练所消费的 self-generated imagined rollout 几何:

- imagined continue
- horizon
- return/base/advantage/weight 的自生成分布

### `bridge`

指 predictive truth 到 actor-use / late-window 消费空间之间的桥接层:

- transition bridge
- terminal truth activation
- hold persistence
- handoff / release / certified floor / capture source

### `authority`

指 SAI 的权威接管层:

- bootstrap trigger / entry
- external authority floor
- task-cert
- authority source recertification
- source replacement 的权威侧接管语义

### `eval protocol`

指实验口径与证据可信度问题:

- `eval_episodes` 变化
- config drift / resolved config 污染
- partial run / early stop / 未完成 run
- 不能做干净 A/B 的样本

## 6. 关键归因结论

### 6.1 `WM core` 不是这段窗口的主故障层

在 `v207-v242` 里:

- 没有任何 run 的主刀口是 teacher-forced `WM core`
- 也没有任何一个近期裁决把失败主因打回 `WM core`

更关键的是，训练代码结构本身就把两条链分开了:

- world model predictive supervision 在 `[aletheia_train.py#L8570](/Users/zhangsan/Desktop/缸中之脑v5.6/aletheia/aletheia_train.py#L8570)` 到 `[aletheia_train.py#L8618](/Users/zhangsan/Desktop/缸中之脑v5.6/aletheia/aletheia_train.py#L8618)`
- actor/critic 使用 imagined rollout 在 `[aletheia_train.py#L14205](/Users/zhangsan/Desktop/缸中之脑v5.6/aletheia/aletheia_train.py#L14205)`
- imagination 时 world model 与 critic 参数冻结在 `[aletheia_train.py#L9031](/Users/zhangsan/Desktop/缸中之脑v5.6/aletheia/aletheia_train.py#L9031)` 到 `[aletheia_train.py#L9037](/Users/zhangsan/Desktop/缸中之脑v5.6/aletheia/aletheia_train.py#L9037)`

所以本窗口内更合理的判断是:

`WM core 不是当前主因层, 至多是上游背景条件`

### 6.2 `imagined geometry` 在本窗口内不是主裁决层

更早文档里，`imagined geometry` 曾被认真怀疑过。  
但到 `v207-v242`:

- 主实验刀口已经转移到 `authority` 和 `bridge`
- 近期失败更像 semantic authority / hold handoff / post-transition capture 语义不稳
- 而不是再次回到 “teacher-forced WM loss 正常但 imagined continue 先坏” 的主诊断

因此:

`imagined geometry` 在本窗口内更多是背景层, 不是主实验归因层

### 6.3 `authority -> bridge` 是这段窗口真正的迁移路径

这 36 个版本段最清晰的迁移是:

1. `v207-v220`: 先不断证明 authority 侧方向是对的, 但只改 authority 不够
2. `v221-v237`: 问题上移到 bridge, 尤其是
   - source replacement
   - transition bridge
   - terminal truth activation
   - hold persistence
   - handoff / release / certified floor
3. `v238-v242`: 开始出现更明显的口径问题, 需要把 eval protocol 从代码本体里剥离出来看

### 6.4 `eval protocol` 是最近窗口里必须单独建账的层

最典型的是:

- `v214` 只有 `2` 个 eval 点
- `v225` 有多个 preview / partial / rerun
- `v238` 有明确 config drift
- `v239-v242` 切到了 `15 episode` 口径

所以从今天起:

- `5 episode` 旧窗口
- `15 episode` 新窗口

必须分开建基线，否则会持续误判。

## 7. 推荐使用方式

后续讨论时，统一按下面方式引用:

- 如果要讨论 `bootstrap trigger / task-cert / authority floor`，优先看 `v207-v220`
- 如果要讨论 `source replacement / hold persistence / handoff / post-transition capture`，优先看 `v221-v242`
- 如果要讨论“这是不是 world model 本体精度问题”，本表结论是:
  - `不是本窗口的主因`
  - 当前主线更应该继续看 `bridge + authority + eval protocol`

## 8. 当前正式结论

对 `v207-v242` 的最简正式裁决可以固定成一句话:

> 这段窗口里，系统主故障已经从早期的“上游 imagined 几何疑云”迁移到 `authority -> bridge` 主链，最近又叠加了显著的 `eval protocol` 污染；没有足够证据把当前不过线主因打回 `WM core`。
