## 五、病理与病因

### 病情表现

1. `best=270 @1250`，但后续 current checkpoint 无法保持，`2500 current = 171.2`
2. `critic` 的绝对语义压力持续升高：
   - `step 1500: value_target_gap_abs ≈ 14.01`
   - `step 2000: ≈ 18.51`
   - `step 2200: ≈ 23.79`
   - `step 2400: ≈ 36.84`
   - `step 2500: ≈ 29.62`
3. `real_mc_value_gap_abs` 同步升高：
   - `1500 ≈ 15.97`
   - `2000 ≈ 27.41`
   - `2200 ≈ 26.07`
   - `2400 ≈ 34.16`
   - `2500 ≈ 34.65`

### 当前病灶

当前最窄病灶已经不是：

- registry 不存在；
- contract 路没接上；
- actor 完全跑飞；
- controller 没有救火。

而是：

> **actor 主合同在高语义压力时，仍主要由 critic/internal proposal 支配；light rebind 只是极小的旁路修正。**

### 根因进一步收紧

这轮 run 暴露出两个更深的结构问题。

#### 根因 1：第一版 alpha law 量级严重不足

当前 alpha 由：

```text
rebind_max
* task_mismatch
* registry_mismatch
* clean_support
```

共同决定。

但实际 run 里：

- `task_confidence` 常年很低；
- `registry_mismatch` 往往只在局部窗口升高；
- 乘法一叠，最终 alpha 只剩 `1e-4 ~ 1e-3`。

这意味着：

> **这条线即使判定“应该接管”，也拿不到足够执行力。**

#### 根因 2：把 `registry mismatch` 当作必要前提，是结构性误判

这轮 run 已经证明，late decline 可以发生在：

- `registry KL` 很小；
- `registry occupancy` 很高；
- 策略仍然留在认证回廊内；

的情况下。

所以如果把：

- `registry mismatch`

当作 rebind 是否启动的必要前提，就会出现一种非常糟糕的情况：

> **系统会因为“还在旧 corridor 里”而判定安全，但实际该 corridor 内部的任务语义已经开始坏了。**

也就是说，当前 `certified corridor` 认证的是：

- `policy proximity`

但没有真正认证：

- `task-semantic correctness`

这就是更深一层的问题。

## 六、为什么这轮结果非常重要

因为它同时把两件事钉死了：

### 1. 不是 actor-side 方向错了

如果方向错了，rebind 不会在真实 run 里稳定出现，也不会在代码与测试中真实改变 actor target / analytic push。

### 2. 但也不是“只要再把 alpha 调大一点”就完了

因为这轮更深的证据是：

- 病情发生在认证回廊内部；
- `registry mismatch` 不是总会升高；
- 也就是说，当前 certified registry 的“安全定义”本身就不够语义化。

所以这不是单纯调参问题，而是：

> **当前 actor contract composer 的接管律和 certified corridor 的认证语义，都还不够对病灶。**

## 七、最新判断

这轮 run 之后，我对系统状态的判断更新为：

### 1. 现状

- actor 主合同重绑定方向：成立
- 第一版 light rebind：过弱
- certified registry：能表达 policy corridor，但还不足以表达 task-semantic corridor
- 当前主病灶：**仍在 actor 主合同的支配权，而不是 corridor 是否存在**

### 2. 当前最根本的原因

> **系统现在缺的不是“再有一条 contract 路”，而是“让真正经过任务语义认证的 contract 在高压时拿到主导权”。**

更具体地说，当前缺的是：

1. `rebind alpha` 的主导式接管律
2. `certified corridor` 的语义再认证

## 八、下一刀建议

下一刀不应该回 controller，也不应该回 critic-only。

最干净的方向是：

> **把 `actor 主合同重绑定 + certified corridor 再认证` 从 light rebind 推进到 semantic-certified dominant contract。**

我建议下一刀分成两个绑定动作，但仍放在同一系统层完成。

### 动作 1：把 `registry mismatch` 从“生死开关”降级

新的主驱动不应再是：

- “只有 registry 不支持时才接管”

而应改成：

- `task-semantic mismatch / clean-target pressure / semantic inflation`
  - 是主驱动
- `registry support`
  - 只作为置信度或上限调制，不再做必要前提

### 动作 2：把 certified corridor 从 policy-certified 升级成 semantic-certified

registry 不能只保存：

- actor snapshot / KL support

还要显式附带：

- replay-grounded task semantics 证书
- clean target 支持证书
- 或最小任务语义包络

只有这样，系统才能识别：

> “还在同一 policy corridor 里，但任务语义已经坏了”。

## 九、一句话总诊断

> **这轮真实 run 证明了 actor contract composer 这条主线是对的，但第一版 light rebind 只修到了“合同存在”，没有修到“合同支配”；同时也证明当前 certified corridor 仍过于 policy 化，无法阻止 corridor 内部的语义下滑。**
